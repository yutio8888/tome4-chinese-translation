# 实际 prompt 与流程约束核验

用户要求核实 prompt 和流程是否说明清楚。检查对象：实际 create_agent 下发内容、INPUT、SPEC、FREEZE、STATE；不是只审计划。

## 已明确

- 40条身份、原文/译文、顺序、source_tag、args_order/special和输入边界冻结；三组初次下发同一 prompt。
- 相同上下文、术语、固定源码版本；只读、禁止看其他模型输出、历史意见和当前译文；不创建子agent、不自动修复。
- 中文自然语言、逐条覆盖、四类结论、证据要求；模型意见不作真值。
- 独立非参赛模型先盲审全40，再以匿名claims核验；三方共同OK仍检查；失败与pending单记，暂定参考非人工金标准。

## confirmed 缺口与处理

1. INPUT 只明确“术语不能覆盖源码”，没有直说“英文描述与实现冲突时也以固定源码实际行为为准”。AGENTS有这项上位规则，但应在共同prompt明确，不能依赖各客户端是否同样注入。
2. 四种分类未规定多claim混合时的条目优先级；“实质缺陷”也缺少可操作门槛。v2统一：有证据的错误/遗漏不因轻微降成偏好；纯风格才advisory；存在已证实错误即ISSUE，否则有证据缺口则pending，再否则advisory/OK。
3. 全仓搜索禁令未给固定commit搜索的边界示例；Opus首轮已违反。v2明确：只可搜索输入包和已知相关单文件；新增源码须记录由哪个调用/符号引入；禁止git grep game/或仓库根，无链路路径则pending。
4. 首轮Opus fresh retry追加了范围澄清，其他臂未收到；实际prompt已不同。不能将本轮当严格同prompt试验。保留为协议预试验，v2让三组fresh会话使用相同新prompt和同40条；不混合两轮、不按分数择优。
5. STATE原先只记录运行身份，缺逐dispatch输入/prompt哈希。冻结清单已存在，现从已记录create调用补录exact prompt，明确记录补录时间，不伪称派发前绑定。v2派发前完成绑定，收回再次校验。
6. reference与参赛Sol同属GPT系列，有相关误差风险；输出应称暂定参考下的相对正确率，保留所有争议与敏感性区间，不称人工验证的客观准确率或全库排名。

本审计不改已经派发的INPUT、SPEC或FREEZE；旧结果/重试/错误永久保留。待现有child收获并确认归档后再派v2，保持同一40条有界范围。旧campaign、译文和术语无写入。
