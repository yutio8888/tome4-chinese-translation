## 1. §14.2 的触发证据

援引条款："pilot／连续批次证明 80 条或单 active batch 是主要瓶颈，且人工裁决／修复没有
积压。"两个分句分别核验如下（数据来源与复现脚本见吞吐分析 §1、附录 A）。

**分句一：80 条是主要瓶颈。**

- 恢复后 20 批实测：`r(批量, 周期) = 0.10`，批量与周期时间无相关。
- 批量 ≥48 的 9 批平均 23.2 分钟；批量 <30 的 9 批平均 22.4 分钟。
- 17 项完整门禁（含严格 addon build）平均 82 秒，占批次周期 6.2%。
- n≤3 走单个 full reviewer 的两批（2 条、3 条）周期为 20.6 与 29.0 分钟，与同期四 lane
  批次无差异，说明派发路数也不是主导项。

即：单条边际成本接近 0，成本几乎全部是每批固定开销，因此**批次数量是唯一有效的成本变量**，
而批量上限直接决定批次数量。

**分句二：人工裁决／修复没有积压。**

- 恢复后 20 批共 887 条，surface ISSUE 0 条、adjudication 0 条、修复项 0 条。
- 队列当前 R = 0，`I 中尚无当前审核` = 2。
- 最后一个非零 ISSUE 批次为 2026-09-04T22:38（4 条），此后连续 20 批为 0。

**两个分句同时成立，§14.2 的触发条件满足。**

## 2. 真正的约束在哪里

### 2.1 三处 80 不是同一个 80

| 位置 | 约束对象 | 性质 |
| --- | --- | --- |
| `production_review_v2_lite_batch.py:17` `MAX_BATCH = 80` | 一个 batch 的 `selected` 条数 | 实现常量 |
| 方案 §5 "默认/硬上限 80" | 同上 | 方案条款 |
| surface 契约 §三 `4≤n≤80` 四 lane；`n>80` fail closed | **单次 screen 的条数** | 消费者契约 |

前两处是同一个上限的两种表述，改动成本低。第三处是独立约束，作用在 screen 层。

### 2.2 为什么第三处会卡住

方案 §266 规定 adapter 按 `(fixed_source_identity, terminology_snapshot, rules_version)`
精确值把一个 batch 分组为同质 run，每个 run 按 surface 契约的 `n=1..3 full`、`n=4..80 四 lane`
派发。因此**每个 run 必须 ≤ 80**，而不是每个 batch。

剩余 27,602 条只有 **4 个** 不同的 `fixed_source_identity`：

| identity | 条数 | 覆盖组件 |
| --- | ---: | --- |
| `commit:624a6732…` | 21,169 | engine + boot + tome |
| `snapshot:c49975dd…` | 3,663 | orcs |
| `snapshot:ed0b1126…` | 1,933 | cults |
| `snapshot:104ad823…` | 837 | ashes-urhrok |

按现行排序模拟装箱的结果：

| 上限 | 批次数 | 平均 run/批 | 最大 run | 含 run>80 的批次 |
| ---: | ---: | ---: | ---: | ---: |
| 80 | 346 | 1.0 | 80 | 0（0%） |
| 160 | 173 | 1.1 | 160 | 170（98%） |
| 240 | 116 | 1.1 | 240 | 115（99%） |

也就是说：**上限一旦超过 80，几乎每一批都会产生超过 80 条的同质 run**（例如 cap240 的前三批
run 规模为 `[182,37,21]`、`[214,20,6]`、`[144,74,22]`）。语料同质度太高，分组无法把 run
自然切到 80 以下。

### 2.3 carry-over 不能用于生产批次

surface 契约 §三 为 `n>80` 提供了 `split_carry_over`：排序后前 80 项进本批 screen，其余
**保留给下一批**。但方案 §266 同时要求 validator 证明"validated union 重排后逐项精确等于
`selected`"——一个 240 条的 batch 若只 screen 掉 80 条，其余 160 条没有结果，守恒证明不成立。

这一点在实现上是自洽的：`production_review_v2_lite_batch.py` 全文没有任何 carry-over 引用，
carry-over 只存在于 `surface_screen_manifest.py` 与 `ai_state_check.py` 的 task 层。生产批次
路径从设计上就要求每个 run 在本批内完整完成。

**结论：单独把 `MAX_BATCH` 从 80 提到 240，不会带来接近 3 倍的收益；每批仍只能完成一个
80 条 screen 加若干小 run，其余条目无法在本批闭合。**

## 3. 申请的最小机制

**申请项：允许一个同质 run 在同一批内被确定性地切分为多个 ≤80 条的并列 screen，
并相应把 `MAX_BATCH` 提高到 240。**

具体地：

1. **run 内分屏。** 当同质 run 的条数 `m > 80` 时，按已冻结的 parent selected 顺序切成
   `ceil(m/80)` 个连续分片，每片 ≤80，各片按现行 surface 契约独立走 `n=1..3 full` 或
   `n=4..80 四 lane`。分片边界由 `m` 唯一确定（前 `m mod k` 片长度 `+1`，与现行 lane 切分
   规则同构），不引入新的自由度。
2. **守恒证明扩展一层。** 现行 validator 证明"各 run 不相交、并集等于 selected"；扩展为
   "各 run 的各分片不相交、并集等于该 run，各 run 并集等于 selected"。这是同一守恒关系
   多一层嵌套，不改变证明方法。
3. **`MAX_BATCH` 80 → 240**，同步方案 §5、§6 的表述与 `stable_selection` 的错误文案。
4. **不使用 carry-over。** 生产批次路径保持"本批内全部闭合"，carry-over 仍只属 task 层。

**为什么这是"最小"的。** §14.2 要求只批准解决该证据的最小机制。证据是"批次数量是瓶颈"，
而批次数量由"每批能闭合多少条"决定，后者当前被 screen 的 80 条上限锁死。分屏是解除该锁的
最小改动：它不新增 consumer schema、不修改 surface 契约的 payload 形状、不改变 lane 规则、
不触及 identity 计算，只是允许同一 run 派发多次现有的 screen。

**替代方案（更小，但收益也更小）：** 只做吞吐分析 §11 的第 1 项——停止按
`fixed_source_identity` 切批、按 80 装箱——**不需要任何契约或代码改动**（§2.2 的模拟显示
cap80 下 `run>80` 的批次为 0）。若维护者不愿改动 surface 契约的分屏语义，应当只做这一项，
并放弃本提案。两者不冲突：装箱是分屏的前提，应当先做。

## 4. 未知量：编排开销是否随批量增长

§1 的 `r = 0.10` 只在 **2–80 条**区间内成立，不能外推到 240 条。一个 240 条的批次相比
80 条批次会带来：

- 逐条固定源码核验的条数增加 3 倍（这部分成本按条计，不是固定开销）；
- screen 数从 1 增至约 3–5，lane 派发从 4 路增至 12–20 路；
- 结果导入、校验与守恒证明的对象增加 3 倍。

其中派发路数的影响取决于并发上限。交接文档记录的操作实践是"最多同时运行三名 child"，
但**我在编排契约中没有找到对应的不变量**——`paseo-orchestration-v2-contract.md:522` 只对
Phase 1 lane 数（2–4）作了规定。请维护者确认这个 3 是 provider 限额还是操作选择：若是后者
且可放宽，20 路 lane 可在更少的波次内完成，收益接近线性；若是硬限额，240 条批次需要约 7 个
派发波次（对比现在的 2 个），收益会被显著吃掉。

**因此本提案申请分阶段验证，而不是一次到位：**

1. 先执行 §3 的替代方案（按 80 装箱），取得 5 批稳定基线；
2. 实现分屏 + `MAX_BATCH = 160`，跑 3 批，实测每批周期与 screen 数的关系；
3. 只有在第 2 步显示周期增幅低于条数增幅时，才提到 240。

若第 2 步显示周期几乎线性增长于条数，说明成本结构已经从"固定开销主导"转为"按条主导"，
此时应当**停止提高上限**，把优化目标转向减少每条成本（去重、lint 前移）。

## 5. 修正后的收益估算

剩余 27,602 条，按每批 22 分钟基线：

| 情形 | 每批条数 | 批次数 | 估算工时 | 需要的改动 |
| --- | ---: | ---: | ---: | --- |
| 现状（实测均值 44/批） | 44 | 627 | 227 h | — |
| 仅按 80 装箱 | 80 | 346 | 127 h | 无（操作实践） |
| 分屏 + 上限 160，**若**周期不随条数增长 | 160 | 173 | 63 h | §3 全部 |
| 分屏 + 上限 240，**若**周期不随条数增长 | 240 | 116 | 43 h | §3 全部 |
| 分屏 + 上限 240，**若**周期随派发波次线性增长 | 240 | 116 | 约 81 h | §3 全部 |

最后两行的差距（43 h 对 81 h）正是 §4 要通过分阶段验证消除的不确定性。**在第 2 阶段实测
之前，任何单一数字都不应当被当作承诺。**

需要注意：装箱一项（127 h，无需任何授权）已经拿到了从 227 h 起总收益的 **54%**；分屏的
增量收益是在此基础上的 63 h 或 81 h。若维护者对改动 surface 契约的分屏语义有顾虑，
只做装箱是完全合理的选择。

## 6. 风险

- **守恒证明的复杂度上升一层。** 这是本提案唯一触及正确性保证的地方。分片守恒必须与
  run 守恒同样是精确逐项证明，任何"抽样验证"的退让都不可接受。建议在实现前先补齐
  方案 §13 风格的边界测试：`m=80`、`m=81`、`m=160`、`m=161`、单分片退化为现行路径。
- **单批失败的代价变大。** 240 条批次若在最终复审或门禁失败，重做成本是现在的 3 倍。
  现行的 checkpoint 与安全边界机制不变，但实际损失面扩大。
- **`r=0.10` 的外推风险**（§4）。
- **观察窗口只有 20 批、一个工作日。** 887 条零 ISSUE 的记录同时也是
  [吞吐分析](review-throughput-analysis-20260905.md) §7 未解释的现象；若其成因是筛查灵敏度
  下降而非语料分布（H2），扩容会把无效审核放大 3 倍。**本提案建议在第 2 阶段之前先完成
  该文 §7 的 canary 校验**，否则应在批准记录中明确写下"未验证灵敏度"这一已知风险。
- **本提案不解决排序退化问题。** 吞吐分析 §6 指出优先键对剩余条目已无信息量；扩容只是更快
  地走完同样的随机序，不会更早发现问题。

## 7. 明确不申请的内容

按 §14.2 "不自动批准多 writer、额外历史层或新 consumer" 与方案 §14.1 的停止条件，本提案
**不**申请：

- 第二个 writer、第二个 active batch、第二个 queue store；
- 新的 consumer schema 或对 surface 契约 payload 六键形状的任何改动；
- 修改 lane 数（保持 4）、lane 切分规则或 lane-neutral briefing；
- 生产批次路径引入 carry-over；
- 改变 `deep_required` 判定、深审抽检比例或收敛下限；
- 改动优先键 `policy-v1.json`（另案，见吞吐分析 §11 第 6 项）；
- push、PR、发布或任何 P3 事项。
