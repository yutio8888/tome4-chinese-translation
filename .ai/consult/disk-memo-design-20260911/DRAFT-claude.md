# 磁盘级内容标识记忆（disk-level content-identity memoization）— 设计草案

作者：优化者（claude）  日期：2026-09-11  状态：**草案，不落地**，供与 gpt-6 的设计对照

数字标注约定：**[实测]** = 我本轮亲自跑出来的；**[转述]** = 主编排者实测、我未复核；
**[估算]** = 由前两类算出来的推论。

---

## 0. 一句话

**不是新机制。** 进程内的内容标识记忆已经在生产里跑了半个月，就是
`tools/i18nlib/git_evidence_reader.py`。这份草案只做一件事：把那张备忘表搬到磁盘上，
并逐条论证「搬过去之后，原来让它安全的每一条性质还成不成立」。

凡是不能论证的，就不搬。

## 1. 进程内版本长什么样（现状，不是提案）

`git_evidence_reader.derive(root, kind, identity, load)` —— 一张
`(kind, identity) -> 已算出的值` 的表，活在一次 `projection_scope` 里，退出即清空。

目前两个调用点：

| 调用点 | kind | identity 怎么来的 |
|---|---|---|
| `queue.py:199` | `catalog` | `sha256` over 全部 `CANDIDATE_FILES` 的 `路径:blob_oid` 对 |
| `queue.py:1046` | `ancestry` | `f"{ancestor}:{descendant}"`（两个 commit OID） |

第一个是这套键设计的范本，值得抄：它**不用路径、不用 mtime、不用 treeish 别名，只用
blob OID**。blob OID 本身就是内容的 sha1，所以「identity 相同」⇔「字节相同」，而
`validate_catalog_files` 只吃字节 —— 相同字节不可能验出不同结果。键完全决定值，
备忘才是纯粹的备忘，而不是第二个事实来源。

`git_evidence_reader.read` 里那段把 `HEAD:path` 先 `rev-parse` 再 peel、
**别名一律不进缓存键**的处理，是同一条纪律的另一面。

## 2. 搬到磁盘上，变了四件事

这是整份草案的核心。其余章节都是这四条的推论。

### 2.1 寿命超过了代码

进程内表活不过 `_projection` 的一次调用，所以「算这个值的代码」在表的生命周期里
**不可能变**。磁盘上的条目会活过 `git pull`、活过我们自己改 `tools/`。

⇒ **工具链闭包指纹必须进键**，这在进程内版本里是可以省的，在磁盘上省不得。

现成的反例就摆在眼前：`TRACKED_LIMIT` 现在是 `134217728`（`production_review_v2_lite.py:26`），
维护者已裁定抬到 512 MiB。它在四处被读，其中 `queue.py:620-621` 拿**当前**常量去校验
**历史** `gates.json`。如果某个记忆条目的计算路径读过这个常量，而键里没有它，
抬限之后旧条目会静默地继续给出旧结论 —— 这不是假想的风险，是这周就会发生的事。

### 2.2 别的进程能写它

进程内表在地址空间里，除了本进程谁都碰不到。`.artifacts/` 下的文件，任何有文件系统
权限的东西都能写。见 §7 威胁模型。

### 2.3 会损坏、会截断、会半写

进程内表不存在「读到一半的 dict」。磁盘上存在。
⇒ 所有读路径必须**坏即未命中**，而不是坏即报错，更不是坏即当真。

### 2.4 它天生是跨进程复用 —— 必须正面回答

我和主编排者本轮已经立过一条规矩：**只去掉同一进程内的重复重放，绝不去掉跨进程的
独立验证。** 磁盘记忆按定义就是跨进程复用，所以必须解释清楚它为什么不违反这条。

分界线在于「复用的是什么」：

- `queue check` 存在的意义是回答「**在一个全新进程里，重放还能不能重现出同一个投影**」。
  它是一次独立复算，不是一个算得快的函数。
- 磁盘记忆复用的是**纯子计算的结果**（这批字节验证通过、这条路径的发布提交是 C）。

所以规矩的落法是：**验证者绕过缓存，是它的定义性质，不是一个可调开关。**
`queue check` 必须在「缓存视而不见」的模式下跑完整重放。这样一来：

1. 独立验证仍然独立 —— 它一个缓存条目都不读；
2. 缓存变成**可证伪的**：只要它撒过一次谎，下一次 `check` 就会对不上 8 字段；
3. 「缓存删掉会怎样」有了标准答案：只会变慢。

反过来说，**任何让 `check` 变快的缓存提案都应当直接否掉** —— 那正好是在拆掉唯一能
发现缓存说谎的那个东西。

## 3. 键

```
key = sha256( kind ‖ content_identity ‖ closure_fingerprint )
```

三段缺一不可：

- **`kind`** —— 哪个函数。防止两个计算撞进同一个命名空间。
- **`content_identity`** —— 这次计算读到的**全部**输入的内容标识，且只能由
  Git 对象 ID 构成（blob OID / tree OID / commit OID）。
  - 路径**不得单独入键**，只能和它的 OID 成对出现（`queue.py:199` 已经是这么做的）。
  - `_publication_commit` 这类依赖提交图的计算，键里必须含 evidence head 的 commit OID
    —— 那一个 OID 把整段历史都钉住了。
  - 因为 OID 是内容哈希，**跨仓库、跨 worktree 天然安全**：同一个 OID 在哪都是同一份字节。
- **`closure_fingerprint`** —— 算这个值的代码的传递闭包：函数自身及其调用到的全部函数
  的源码哈希 + Python 版本 + **它读到的每一个模块级常量**（`TRACKED_LIMIT`、
  `CANDIDATE_FILES`、`PRODUCTION_PREFIXES` …）。

第三段是全案最容易做歪的地方。老老实实的做法是**手工登记**：每个可缓存计算显式写出
自己的闭包清单，配一个单元测试断言「清单里的东西变了，指纹就得变」。
自动 AST 推导看着聪明，漏一条就是静默陈旧，而静默陈旧正是这套信任模型最不能忍的失败方式。
宁可手工、宁可保守。

## 4. 存什么、不存什么

**存判定与摘要，不存解析产物**（这一条我采纳 fable 5 的 §4）。

| 存 | 不存 |
|---|---|
| 「这组字节验证通过」+ 结果摘要 | 重建出来的 entries / overrides 列表 |
| 「路径 P 在 head H 下的发布提交是 C」 | 整个 projection 元组 |
| 「A 是 B 的祖先」 | 任何 SQLite 行 |

量级：**每条几十到几百字节**[估算]。

三个理由：

1. 小 ⇒ 校验和存储都便宜，整张表可以一次读完。
2. 存产物等于让缓存变成第二个事实来源 —— 一个被改过的产物会直接污染投影；
   而一个被改过的判定，最多让我们**跳过**一次检查。两者的最坏情况差一个数量级。
3. 产物的形状会随代码演进，判定不会。

**只缓存成功，不缓存失败。** 失败恰恰是最需要每次重算的东西（修好了得能立刻看出来），
而且一条被缓存的失败可以把整条流水线钉死。这条同时让「缓存缺失永远安全」成立。

## 5. 失败关闭清单

- 位置 `.artifacts/`（`.gitignore:6` 已忽略）—— **永不提交、永不随证据分发**。
- 删掉整个缓存只影响速度，不影响任何结论。这必须是一条可执行的测试，不是一句承诺。
- 读失败 / 解析失败 / 版本不符 / 键不认识 ⇒ **未命中**，继续全量算。
- 写入原子化（临时文件 + `rename`），半写的条目在下次读时表现为未命中。
- 缓存格式自带版本号；版本不认识就整张表当空的。
- 工作树脏不脏与缓存无关 —— 键全是 Git OID，这是**构造上的**无关，不是约定。

## 6. 值多少

主编排者的干净剖面[转述]：一次完整重放 167.8s，其中

| 项 | 耗时 | 占比 |
|---|---|---|
| `validate_catalog_files` | 71.3s | 42.5% |
| `reconcile` | 34.8s | 20.7% |
| `_publication_commit` | 34.7s | 20.7% |

我在隔离 worktree 的完整重放是 172.9–177.9s[实测]，同一量级。

**最大的一块正好是最适合磁盘化的那块。** `validate_catalog_files` 的 71.3s 是**已经**
被进程内记忆去重之后的数字 —— 代码注释说一次重放覆盖约 43 个不同的 catalog 内容，
即约 **1.7s/次**[估算]。而每批只新增一个 catalog，所以一张热的磁盘表下，
这 71.3s 会塌成约 **1.7s**[估算]。

`_publication_commit` 的 34.7s **不该用缓存解决** —— 见 §8。

## 7. 威胁模型（不粉饰）

能写 `.artifacts/` 的攻击者，可以伪造一条「验证通过」的判定，让我们**跳过**一次真实校验。
这是真实存在的洞。

我的判断是**接受它并写明白**，理由：能写 `.artifacts/` 的东西同样能写 `tools/`，
而信任模型对「工作树被改」的回答从来就不是「工作树里再加一层防御」，而是
**已提交的证据 + 在干净检出里跑 `queue check`**。给缓存加 HMAC 只是把同一个信任边界
往里挪了一格，不改变它在哪。

真正要写进文档的是这一句：**缓存的威胁模型 = 工作树的威胁模型，不高不低。**
谁要是开始拿缓存的结论当证据用，那一刻这条就破了。

**修正（主编排者 2026-09-11 指出，我接受）：** 上面这段只谈了恶意攻击，漏了另一类。
缓存还会**非恶意地**坏掉——半截写入、崩溃残留、位翻转。对这一类，载荷 MAC／摘要
校验的价值不在「防攻击者」（那确实防不住，攻击者能改 `tools/` 就能改指纹），
而在于让**坏掉的条目表现为未命中，而不是表现为一条被采信的判定**。

所以是两道，不是一道，且互不替代：

1. **只存判定（§4）** —— 把爆炸半径限死在「跳过一次检查」。这是主要缓解。
2. **载荷 MAC／摘要** —— 把「损坏」从「静默采信」降级成「未命中」。这是第二道。

§5 里那条「读失败／解析失败 ⇒ 未命中」本来就是这个意思，但只靠「解析得通」是不够的：
一个位翻转完全可以翻出一个仍然合法的 JSON。所以必须是**载荷摘要校验**，不是解析成功即可。

## 8. 排序原则：能改算法就别加缓存

`_publication_commit` 是现成的例子。

- 现在：每条路径一次 `git log`，中位 **21.6ms**[实测] × **2,532** 条路径[实测]
  ≈ **55s/次重放**[估算]（编排者剖面里是 34.7s[转述]，机器负载不同，同一量级）。
- C1 方案：一次前缀级 `--name-status`，**23.8ms、258 KB 输出**[实测]。
  我已核对：**当前触及证据的 merge commit 为 0 条**[实测]。

**但「现在 0 条」不等于「将来 0 条」，这一点必须写进设计而不是留作补丁。**
主编排者指出仓库里已有 `test_merged_sibling_identical_publications_are_rejected_as_ambiguous`
（`tests/i18n/test_production_review_v2_lite_queue.py:875`）：两个 sibling 分支各自发布
一个**内容相同**的批次，再 `git merge --no-ff` 合起来，`_publication_commit` 必须报
「one commit」把它判为歧义。我已复核该测试确实构造了这个场景。

所以「0 条 merge commit」只是说**快路今天恒命中**，不是说慢路可以不存在。
任何前缀级／可达图重建都必须带一条**明确的回落**：条件不满足就退回全算法，
而不是在快路上猜一个答案。gpt-6 的 §3.5 走的是可达图路线（仅当 B 的单父 child 恰为 `[C]`
时走快路），路子和 C1 不同，但那条回落是对的，应当保留。
**「失败关闭」是这类改动的设计前提，不是事后加的防御。**

一个缓存能让错算法变快，但**每一次冷启动都要付全价**：新 worktree、新克隆、CI。
所以顺序应当是：

1. 先把能算得更少的算法改掉（C1、组清单去重）；
2. 剩下真正不可约的纯计算，才上磁盘记忆。

反过来做，就是拿缓存把一个本该消失的开销永久固化下来。

## 9. 未决问题（我没有答案，应当由维护者或设计核验回答）

1. **闭包指纹用手工登记还是自动推导？** 我倾向手工（§3），但这会给每个可缓存计算
   加一份维护负担，需要确认可接受。
2. **缓存条目要不要设上限 / 淘汰？** 键含 head OID 的条目（如 `_publication_commit`）
   每批都会产生一整代新条目，会无界增长。最简单的答案是「按 evidence head 分代，
   只留最近 N 代」，但这需要确认 N。
3. **CI / 新克隆的冷启动预算是多少？** 这决定了我们能容忍多少「只有热缓存才够快」的设计。
4. **`queue rebuild` 的自检要不要也绕过缓存？** 按 §2.4 的逻辑它是同进程自检，
   本来就发现不了「重放不可重现」，绕不绕过都不改变它的能力 —— 但绕过会让它变慢。
   我倾向不绕过，理由是 `check` 已经承担了这个职责。

## 10. 不落地

本草案不含任何实现，我不会自行实施其中任何一条。
提交它只是为了和 gpt-6 的设计（`b670fe18`）并排看。

两份设计最值得对照的是这四处：键里有没有工具链闭包、存判定还是存产物、
`queue check` 是不是强制绕过、以及有没有把「先改算法再上缓存」的顺序写进去。
