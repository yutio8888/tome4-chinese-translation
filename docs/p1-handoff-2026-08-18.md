## 5. 已获得的操作经验（避免重复踩坑）

### 5.1 SCOUT 路径：定位不可信，结论多数属实

四批侦察的一致模式：**代码内容引用逐字正确，长文件里的行号偏 2–3 行**。加指令无法根除。

更严重的两次：

- 一次**编造 git commit hash** 来支撑「该机制在某次提交被移除」——它读的是固定检出点，
  无从验证提交历史；
- 一次把天赋定位到错误行段，并描述了**另一个天赋**的 info 体。

**操作规则：只信内容，不信行号；任何涉及 git 历史的断言一律丢弃。**
派发 briefing 里应固定包含「禁止引用 git 历史」与「不确定就给符号名并标注未确认」。

净收益仍是正的（省掉「去哪儿找」的时间），但每条关键行必须回核。

### 5.2 风险 flag 高度共现，单选一个 flag 不等于隔离一个维度

tome mechanics 池中，822 条带条件 flag 的里有 709 条（86%）同时带数值 flag。
直接按条件 flag 抽样，会得到 23/24 仍是数值项的批次，与前一批毫无对照价值。

`tools/p1_select_batch.py` 已支持 `--exclude-risk-flag`（可重复）。但要注意二阶效应：
排除数值 flag 后，剩下的多是分类/风味文本，`profile-uncertain` 占 73/113。
最终还需再排除 `profile-uncertain` 才得到与 B1 可比的 40 条池。

**冻结批次前先看构成分布**（目录、source_tag、profile 确定性），不要只看 flag 命中数。

### 5.3 判定前必查的三件事

三次险些误判，都是靠核查避免的：

1. **占位符重排可能是合法的**。`I18N.default_tformat` 支持 `args_order` 重映射，
   译文条目以 `t(src, dst, tag, args_order)` 第 4 参数声明。批次记录里也有 `args_order` 字段。
   看到译文重排顺序，先查是否声明。
2. **术语要查语料频次，不能凭直觉**。`Defense → 闪避` 在语料中是 127:25 的主流，
   凭印象判「应作防御」会冤枉现译。
3. **源码本身可能有笔误**。`temporal-hounds.lua` 向只有两个占位符的格式串传了四个实参，
   抗性显示的是防御值。此时译文保持两个占位符才是对的——多写一个会吃掉 `defense/2`
   并改变显示值。按判定依据，以实际显示为准。

### 5.4 legacy 不可达条目

两批各出一条运行时永不显示的译文（B1 的 `EFF_DUAL_WEAPON_DEFENSE`、B2 的 Pity）。
累计 2/48 ≈ 4%。判定方法：查天赋树是否被 `load()`、类型是否被声明、写入的属性是否有读取点。
三项皆否才算死代码，**不采信任何关于「何时被移除」的说法**。

尚不足以支撑在选择脚本里加可达性过滤，但值得继续计数。

### 5.5 语境审核（`translation_contextual_v1`）的实操

- 契约要求输出为单一紧凑 JSON，且 `evidence.source/target` 与冻结字节精确一致。
  **回显长文本是主要失败面**：一次 7 条的派发因模型在最后一条字段值后追加解释文字而整份作废。
- 有效对策：**拆小 bundle**（4+3 优于 7），并在 `rendered_briefing` 里显式写明
  「字段值之后不得追加任何解释文字」「identity 只需原样回显、不要计算摘要」
  「输入是单行紧凑 JSON，请用 JSON 解析器读取」。
- `rendered_briefing` 在 payload 内部，是**合法的指令位**；改它只产生新候选，不触碰契约。
- 审核确实抓到过宿主漏掉的缺陷（B1 的 F8：`apply Counterstrike` 的施加方向），
  所以这一步不是形式。

### 5.6 每批译文改动的连带影响

改规范译文会改变 `translation_inputs_sha256`。该耦合已在 `0ffe057` 修复，
**新批次不应再撞到抽样测试的四个断言**。若再次撞上，说明抽样行为真的变了，应当认真排查
而不是更新常量。
