# 审核流程与工具优化方案

## 0. 文档状态与目标

本文是一份优化实施方案，不是当前工具契约。它基于 2026-09-05 对 commit `f6b2f85` 的只读分析，
针对 AI 自动化译文审核流程及非翻译工具文件提出六项改进，并给出优先级、验收条件和边界。

本文不改变任何译文质量标准。凡涉及审核策略（例如深审分流规则、抽样比例）的调整，
均单独列为“策略事项”，需要作为跨批次裁决另行确认，不得在工具重构中顺带修改。

分析时运行了 doctor、Paseo 契约检查以及 84 项相关测试，全部通过；未运行完整构建门禁，
未启动新的译文审核，工作树未改动。

## 1. 现状结论

### 1.1 保留的骨架

当前流程为：

正式 catalog → 每批最多 80 条 → 表层审核 → ISSUE 进入语境深审 → 主代理按源码裁决
→ 必要时修复并独立复审 → 门禁 → 提交 evidence → 重建队列状态。

以下设计已验证有效，本方案全部保留：

- 固定源码 commit 优先，DLC 来源未固定的事实持续记录；
- 候选身份冻结，批次内 revision identity 不漂移；
- 审核角色分离，模型观察与主代理裁决分离；
- SQLite 仅作运行时状态，可从 Git 证据完整重建；
- 单机、单维护者、单工作树 writer，仓库级排他锁。

### 1.2 已确认的问题

| 编号 | 问题 | 证据 | 性质 |
|---|---|---|---|
| P1 | 完整门禁的测试清单遗漏 wave、executor runner、allowed files 三组测试 | `tools/ci-gates.sh` 显式清单；三组测试补充执行均通过 | 持续验证覆盖缺口 |
| P2 | 批次门禁封装先跑 doctor、lint、消费者测试，再调用包含相同检查的完整 CI | `production_review_v2_lite_batch.py` 约 1400 行处；最近批次 `gates.json` | 重复执行，日志扩展名承担兼容语义 |
| P3 | 队列从 Git 回放历史证据成本高 | 单次回放约 17 秒，queue 模块记录 505 次 Git 子进程调用（cat-file 276、log 190） | 性能，单次观测 |
| P4 | 进度报告未区分表层通过与深审通过 | 六个批次 480 条历史记录中 407 条仅有表层结果、73 条进入深审 | 报表语义 |
| P5 | 大文件耦合与契约检查依赖文本包含 | `cli.py` 约 4,134 行、`ai_state_check.py` 约 2,711 行、`test_toolchain.py` 约 19,638 行；`paseo_contract_check.py` 以去空白文本包含校验 | 维护成本 |
| P6 | DLC 访问模型与 doctor 检查边界混用 | doctor 因 engine 仓库含 protected source 跳过整个工作树扫描 | 语义混淆 |

## 2. 实施顺序与总体原则

实施顺序：**P1 → P2 → P3 → P4 → P5 → P6**。前三项证据直接、边界清楚、收益可测；
P4 需要先定义指标再改报表；P5、P6 为渐进整理，可与其它工作并行推进。

总体原则：

1. 每项改动独立成任务、独立提交，附带其验收条件的执行记录。
2. 不删除任何现有检查；重复只能合并，不能移除。
3. 任何优化前后，对同一 commit 的队列投影、证据文件和门禁结论必须逐字节一致，
   除非该差异正是本任务的目标并已在文档中说明。
4. 兼容历史证据：已提交的 `evidence/` 目录不改写，读取端负责兼容旧格式。

## 3. 分项方案

### 3.1 P1：补齐门禁测试覆盖

**目标**：完整门禁不再依赖手工维护的长命令，新增测试文件不会被遗漏。

**改动**：

1. 新增单一测试分组清单文件（建议 `tests/i18n/test_groups.json` 或等价 Python 模块），
   按现有门禁步骤分组列出测试模块；`ci-gates.sh` 从该清单读取，不再内联文件名。
2. 立即将 `test_wave_review.py`、`test_executor_runner.py`、`test_check_allowed_files.py`
   纳入相应分组。
3. 新增一条门禁检查：遍历 `tests/` 下所有 `test_*.py`，凡未出现在任何分组且未在
   显式排除表中登记者，门禁失败。排除表需注明排除原因。

**验收**：

- 完整门禁运行后，三组遗漏测试出现在门禁日志中且通过。
- 人为新增一个空的 `test_zzz.py` 而不登记，门禁失败；登记后通过。
- 现有分组的测试集合与改动前逐项一致（仅增不减）。

### 3.2 P2：统一门禁执行与记录

**目标**：门禁只执行一次，产生结构化结果；批次工具消费结果而不是重复运行。

**改动**：

1. 让 `ci-gates.sh`（或新的 Python 入口）在完成后输出一份结构化 gate results
   （JSON，含每项检查的 ID、命令、退出码、日志路径、开始与结束时间、
   所绑定的候选 revision identity、工具版本与配置哈希）。
2. 批次门禁封装改为：调用统一入口一次 → 读取结构化结果 → 写入 `gates.json`。
   移除封装内单独运行的 doctor、strict lint、消费者测试。
3. 日志扩展名统一；`.log` 与 `.out` 的区分不再承担语义。相关测试改为断言
   结构化结果中的检查 ID 集合，而非文件名集合。
4. 结果复用仅在以下条件全部相同时允许：候选 revision identity、工具 commit、
   配置哈希、检查 ID 集合。任一不同即重新执行。

**验收**：

- 对同一批次，改动前后 `gates.json` 中的检查 ID 集合完全一致，无检查消失。
- 门禁总耗时下降，并在任务记录中给出改动前后各一次测量。
- `docs/agent-workflow.md` 中关于 `*.out` 兼容处理的说明删除，改为描述结构化结果。

**边界**：不改变任何检查的严格程度；不引入跨机器或跨会话的持久缓存。

### 3.3 P3：优化 Git 证据回放

**目标**：降低队列回放时间，同时保持投影完全一致。

**改动**，分两阶段：

阶段 A（低风险）：

1. 在单次命令生命周期内，按不可变的 commit ID 和 blob ID 缓存 `cat-file` 与 `log` 结果。
   缓存键只允许使用完整哈希，不允许使用 ref 名或路径。
2. 保留全部身份、内容哈希与历史校验逻辑；缓存仅减少子进程调用，不跳过校验。

阶段 B（视阶段 A 效果决定）：

3. 将逐个 blob 读取改为 `git cat-file --batch` 单进程流式读取。
4. 若历史批次数继续增长，评估按批次目录一次性读取 tree，而非逐文件 `log`。

**验收**：

- 对同一 HEAD，优化前后队列投影（含全部状态、计数与顺序）序列化后逐字节一致。
- 记录 Git 子进程调用次数与耗时的前后对比，至少测量三次取中位数。
- 缓存不跨命令持久化；新增测试验证同一进程内对同一 blob 只发起一次读取。

**边界**：不引入持久缓存层或数据库缓存；17 秒是单机单次观测，目标以相对下降为准，
不设绝对秒数指标。

### 3.4 P4：分离表层进度与深审进度

**目标**：进度报告能回答“多少条只经过表层审核”“多少条经过语境核验”“多少条待修复”
“多少条因版本变化失效”。

**改动**：

1. 队列状态报告新增四个独立指标，均以当前 catalog 的 eligible 集合为分母：
   - 表层覆盖：存在当前版本表层结果的条目数；
   - 深审覆盖：存在当前版本语境核验结果的条目数；
   - 待修复：裁决为需修复且尚未复审通过的条目数；
   - 版本失效：历史记录存在但 revision identity 已变更的条目数。
2. 报表中不再以单一 `done` 表达完成，`done` 若保留，须明确注明其对应层级。
3. 现有 `completion_level` 字段作为唯一来源，报表只做聚合，不新增平行状态字段。

**策略事项**（本方案不实施，需单独裁决）：

- 对表层 `OK` 条目设置固定比例抽样进入深审，用以测量表层漏检率；
- 是否让机制高风险条目（例如含数值、技能公式、状态效果描述）跳过表层直接深审。

**验收**：

- 对当前 HEAD，四个指标之和与历史记录的分类结果可相互核对，并在任务记录中列出。
- 历史批次 `evidence/` 无需改写即可被新报表正确聚合。

### 3.5 P5：缩减文档重复，按职责拆分工具

**目标**：降低单文件改动影响面，让契约正文集中维护并由行为测试验证。

**改动**，均为渐进式：

1. `cli.py`：按命令族拆分为独立注册模块（例如 doctor、production、quality、contextual），
   顶层只保留命令注册与公共参数。每次拆分一族，拆分前用 `rg` 确认所有消费者，
   拆分后现有 CLI 测试全部通过。
2. `paseo_contract_check.py`：沿用现有 clause ID，检查器只校验“契约文档中 clause ID 集合
   与版本号是否与代码声明一致”，不再存储规范原文副本；条款行为由正反测试覆盖，
   每条 clause 至少一个通过用例与一个违反用例。
3. `test_toolchain.py`：按被测模块拆分为多个文件，并纳入 3.1 的分组清单。
4. 文档：`docs/agent-workflow.md`、`i18n/README.md` 与各契约文档之间的重复段落，
   保留一处正文，其余改为链接引用。
5. 旧代码归档：任何 `pi_*`、旧版 quality 模块，先用 `rg` 列出消费者，
   有消费者的不得归档；`cli.py` 目前仍引用 `pi_quality`，不得按文件名批量删除。

**验收**：

- 每次拆分后完整门禁通过，且 CLI 的 `--help` 输出命令集合不变。
- 契约检查器对删除任一 clause 的契约文档报错；对仅调整措辞的文档不报错。
- 任务记录列出被归档模块及其消费者查询结果。

### 3.6 P6：澄清 DLC 访问模型与 doctor 边界

**目标**：将一个历史分类拆为多个独立属性，避免单一标签同时控制多种行为。

**改动**：

1. 在源码配置中为每个源码仓库或 DLC 分别记录：
   - 公开性（public / protected）；
   - 提取方式（full-tree / lua-extractor-only）；
   - 来源是否固定（pinned commit / unpinned）；
   - 允许扫描范围（路径白名单）。
2. doctor 按“允许扫描范围”决定扫描，而不是因仓库内存在 protected source 而跳过整棵树。
3. doctor 输出中分别显示上述四个属性；DLC 来源未固定的事实必须继续以警告呈现。

**验收**：

- doctor 对 engine 仓库的公开路径执行扫描，警告文本不再出现整树跳过。
- DLC 未固定来源的警告保留，措辞与之前等价。
- 三个官方 DLC 的公开性显示为 public，与上位说明一致。

## 4. 风险与回退

- 所有改动均在 `develop` 分支独立提交；任一项验收失败即回退该提交，不影响其它项。
- P2 与 P3 涉及证据读取与写入路径，实施后须对最近一个已提交批次做一次完整重放，
  确认 `gates.json` 与队列投影一致后再合并。
- 本方案不触碰 `i18n/` 下译文内容与 `evidence/` 历史文件。

## 5. 未包含的事项

- 全量审核的启动时机与批次节奏；
- 表层审核抽样比例与高风险直入深审规则（见 3.4 策略事项）；
- 评估器模型选择与提示词调整；
- 跨机器或持久化缓存。
