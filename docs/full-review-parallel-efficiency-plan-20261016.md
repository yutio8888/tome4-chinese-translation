# 全量译文审核并行提效修订方案

修订日期：2026-10-16。实施顺序为：建立耗时基线，增大合适的后续批次，再按实测瓶颈选择批量准备工具或独立工作区门禁。审核并发作为滚动调度的辅助手段。

本方案沿用 [AGENTS.md](../AGENTS.md)、[代理工作流](agent-workflow.md) 和 [Paseo 编排契约](paseo-orchestration-v2-contract.md)。当前修订只形成实施安排；涉及工具行为、跨工作区执行或消费者校验的改动，须另建有界实现任务并完成适用复审与门禁后启用。

## 现有测量能说明什么

2026-10-15 同一组五条修复后生产复审的历史样本如下，单位为秒：

| 环节 | A | B | 测量口径 |
| --- | ---: | ---: | --- |
| 准备间隔 | 262.2 | 262.0 | scope 文件至导出 ref 文件的修改时间差，属于近似区间 |
| agent 创建至完成标记 | 119.5 | 130.5 | 包括启动和工具读取，不能视为纯模型推理时间 |
| 完整门禁和构建 | 188.9 | 180.3 | receipt 的开始至结束时间 |

准备间隔尚未拆分为上下文编写、锁等待、历史重放、源码校验和发布，不能把整段 4.4 分钟视为可消除成本。各环节可能重叠，分项相加也不是端到端墙钟。

代码确认每次 `export()` 会在 `round_lock` 内调用 `check()`，后者递归检查 predecessor 历史。重复重放值得测量，但开发优先级取决于其实际占比。门禁包含固定检查集，增大批次可能摊薄每条成本；变化后的耗时和审核质量仍须实测。[导出与重放实现](../tools/i18nlib/full_review.py)

历史样本和来源哈希见 [MEASUREMENTS.json](../evidence/plan-review/parallel-efficiency-revision-20261016/MEASUREMENTS.json)。它不提供端到端吞吐基线。

## 共享工作区的调度规则

A 保持 Opus 5.5，B 保持 GPT 6.1 Sol。先采用最多三个活动审核子进程的调度预算，就绪队列充足时尝试 2A＋1B。这个数字是试点上限，不是已核验的 Paseo 守护进程容量；实际可用名额、配额和资源不足时下调，不增设 lane orchestrator。

风险预选的 B 可以与 A 并发。两路使用相同 revision 和中性源码语境，彼此不读取对方意见。由 `A-observation` 新触发的 B，须等到 A 的 ISSUE 原始结果通过现有消费者验证，再冻结新的中性选集；已覆盖的 B 不重复计数。模型出现 429 时保留指定模型并退避，其他就绪任务使用空余名额。按通知收获结果，身份核验、fresh retry 和归档纪律保持不变。

主代理串行发布任务记录和 round 证据。共享工作区采用以下时段安排：

| 时段 | 可同时进行的工作 | 写入边界 |
| --- | --- | --- |
| 准备与冻结，无门禁运行 | 主代理准备下一包；已派发 reviewer 只读审核 | 导出、导入和发布由主代理依次执行 |
| 门禁运行 | reviewer 继续只读；主代理读源码或在内存中起草 | 暂停所有参与门禁指纹的文件、HEAD 和 index 变化 |
| 门禁结束且绑定稳定 | 归档 receipt 和日志、导入结果、更新证据与提交 | 完成发布后才开始下一个门禁 |
| 修复候选 | 按既定窗口集中处理 confirmed 问题 | 唯一 EXECUTOR 写入；先闭合受影响的审阅和门禁，再变更候选或推进 successor |

门禁指纹包含全部已跟踪文件，包括已跟踪但后来被 ignore 的文件，以及未跟踪且未忽略文件。运行期间不得创建或修改 `evidence/` 中的 export、import、报告和其他未忽略输入；只串行门禁而继续发布 evidence 仍会导致失败。门禁进程的环境和输入绑定也须保持稳定。[绑定实现](../tools/i18nlib/gate_results.py)

已忽略且未被候选引用的编排记录、派生计时记录可以更新；冻结 SPEC、envelope 和被引用快照即使位于忽略目录，也必须保持原字节。计时结果可先留在内存或已忽略的派生目录，门禁结束后再归档人工判断和核验锚点。门禁期间不在同一工作区启动其他门禁或构建。

## 先测量并调整批次

下一次原本就要发生的导出，记录命令实际开始和结束时间，并分别观察锁等待、当前候选校验、顶层 `check()`、其中的历史递归、逐条源码与中性语境检查，以及序列化发布。递归调用的累计时间包含子调用，不能把各层 inclusive 时间相加。若使用 profiler，同时记录其开销；若计时必须修改工具，先按工具维护范围验证。

先测量原定操作，不另行重复导出或审核来制造基准。已冻结的任务和工作集保留原边界，已完成的生产结果保持原计数。准备时间或端到端起点缺失时记录为未知，不用文件修改时间补造成函数耗时。

后续未冻结的切片，按同一源码身份和相关技能树聚合。机制说明以 20–40 条、短名称以 60–80 条作为试点目标；它们不是最低条数。每包仍受现有 1–80 条上限、实际 preflight、文本与源码预算约束。过长或跨条关系过于复杂时缩小，不截断上下文或源码来凑条数。[现有导出限制](../tools/i18nlib/full_review.py)

先比较增大批次前后的有效吞吐和返工，再决定是否提高并发。若准备和门禁仍占主代理大部分串行时间，增加审核路数只能减少部分空等，不据此承诺两倍提速。优先处理实测的主要成本。

## 按测量结果选择工具维护

### 批量准备入口

只有当重复历史重放属于主要耗时项，且预期节省足以支持实现和验证投入时，才优先实现一次命令准备多个任务的入口。它须保持现有消费者和失败语义：

1. 只处理一个权威 round，整个批量调用持有其现有 `round_lock`；单一主代理管理有界任务清单。
2. 只在同一次调用中复用已经验证、封存的历史递归结果。当前候选、源码文件、历史封存身份和本轮状态仍须按其实际变化校验；不提供跨命令缓存。
3. 每冻结一个 export，就更新当前 obligations。后续 export 必须看到它，继续检查 A/B 中性对齐、B 适用原因，以及已有当前和继承覆盖；不能把调用开始时的整个 `check()` 结果当作静态缓存。
4. 每个任务独立生成 SPEC、SCOPE、候选、preflight 和身份绑定。批量完成后再执行一次完整 `check()`，全部通过后才派发。
5. 失败时保留已冻结字节和任务记录，停止消费未验证产物，按已有恢复纪律处理。每任务的独立复审、完整门禁、构建和 DONE 验证保持不变。

实际维护另建 Paseo 任务，由 EXECUTOR 唯一写入；普通 REVIEWER 和 SENIOR_REVIEWER 独立检查同一候选，按现行用户模型授权和契约核验精确模型差异。验证须覆盖同批后续 export 的可见性、A/B 不一致、重复覆盖、源码或封存漂移、部分失败恢复，以及新旧消费者重放。

### 独立工作区门禁

先试两路只执行门禁的工作区，分别使用真实独立 Git worktree、实际工作区身份和明确的根目录映射。导出、导入、覆盖裁决和发布继续集中在主工作区，使用同一权威 round；worker 不各自导出或独立推进 round。

启用前须实现并独立复审以下链路：

| 链路 | 必须保持和验证的内容 |
| --- | --- |
| 冻结执行输入 | 固定工具 HEAD、候选、语义 index、manifest、源码身份，以及门禁实际读取的文件；包括已忽略的任务 SPEC／BASELINE 和当前尚未提交的 round 证据 |
| 保留用户工作树 | worker 接收候选的准确快照，不能把干净 HEAD 当作当前候选；主工作区的既有 dirty 不被清空、stage 或并入无关提交 |
| 身份与路径 | 区分审核 producer 的原始 task／workspace／parent 身份与门禁执行根目录；不改写 STATE 或 native cwd 来伪装同一工作区，消费者须明确支持并验证执行映射 |
| 门禁执行 | 每个 worker 同一时刻只跑一个任务，独立保存完整检查集、严格 build、环境身份和起止绑定检查；主工作区不得改变这些任务绑定的候选或工具 |
| 回执接收 | 带回每任务原 receipt 与全部日志，经已验证的归档入口核对哈希、selection、基线、执行输入及环境来源；不靠重写绑定字段使其匹配主工作区 |
| 原子消费与恢复 | 主代理串行验证并发布；输入漂移、缺日志、映射歧义或身份不符时拒绝消费，保留证据并按现有恢复规则重建有效任务 |

`task_gates()` 会读取所属根目录的任务文件和 round 证据；新 worktree 不会自动拥有被 ignore 的 `.ai/task/` 或未提交的 evidence。`validate_task_gates()` 的既有 selection 校验不能独自证明执行输入同步和跨根目录消费正确。执行快照、身份映射及 receipt 接收协议验证完成前，继续在主工作区串行运行。[消费者实现](../tools/i18nlib/full_review.py)

负向验证至少覆盖：任务文件缺失、候选或工具漂移、错误根目录或 producer 身份、B 中性输入不一致、重复覆盖、receipt 被改动、日志缺失及恢复后重复消费。即使 receipt 校验可通过，也须证明其确实对应当前候选和受支持的执行映射。

两路门禁会争抢 CPU、内存和 I/O，先测串行与双路的实际总墙钟、失败和重跑成本，再确定并发数。资源观察只做有界运行记录，不引入常驻监督器。

### 译文修复合并单独处理

wave 的非空 patch 是译文修复并行合并的另一项限制，不是只读审核任务并行门禁的前置条件。当前 wave 仅支持 `changes=[]`；本轮提效保留修复窗口的唯一 EXECUTOR，不把非空 apply 实现纳入门禁 worker 维护范围。[现行边界](paseo-orchestration-v2-contract.md)

## 吞吐基线与试点验收

主要指标为：固定试点选集中，满足当前 revision 的 A、适用 B、逐条源码核验、裁决、门禁、DONE 和提交要求的唯一 unit 数，除以从该组第一次准备开始到最后一次范围内提交结束的墙钟小时数。

A 与 B 不相加，同一 unit 的重试或旧 revision 不增加完成数。来源或运行时 pending 不算完成。修复和复审数量另外报告，不能用重复审核填高吞吐。跨批次交叠时，按整组最早开始、最晚结束计算，不累加重叠的分项时间。

基线按以下步骤建立：

1. 先检查最近三个可比批次是否具有完整的准备起点、提交终点和有效完成数。历史样本的分项时间可作参考，缺失的端到端时间不能据此推算。
2. 若历史记录不足，在原定审核顺序中前瞻记录三个自然发生的有界基线批次；所有条目只计一次生产覆盖。
3. 试点选择源码身份、文本量、机制复杂度、A/B 风险比例相近的批次。保持源码与质量规则、环境和可选投影缓存设置可比较；工具版本变化单独注明。
4. 先测只改变批量的效果，再测只改变审核路数的效果；批量准备工具和双 worker 分别比较。若无法分离变量，就只报告组合收益，不归因单个优化。

每个批次记录：输入条数和字节数、源码语境量、A/B 数量和风险原因、准备／锁等待／导出及历史重放／agent／门禁／导入裁决／修复／提交的起止时间、重试与 429、最终有效完成数，以及有界资源观察。外部等待和用户暂停单列，端到端总墙钟仍保留。

基线和可比试点均完成后计算吞吐比。两倍是试点目标，不是当前测量结论；未达到时按分项数据调整投入，不能降低源码覆盖、门禁或复审要求来达标。只改善模型用时或每批成本时，按对应指标报告。

## 实施次序与意见处理

| 次序 | 动作 | 进入下一步的条件 |
| --- | --- | --- |
| 1 | 在原定批次中补齐实际命令计时和吞吐基线 | 数据能区分准备、历史重放、模型和门禁成本 |
| 2 | 在未冻结切片试较大且语境完整的批次，按就绪情况尝试最多三路审核 | 质量和返工通过，能与基线按相同口径比较 |
| 3 | 选择实测主要瓶颈对应的维护：批量准备入口或独立门禁 worker | 独立实现、复审、兼容及恢复验证通过，再进入有限生产试点 |
| 4 | 用三个可比试点批次评估端到端收益 | 报告真实收益、开销和失败情况后确定后续调度 |

原 Opus 5.5 意见与处理关系如下。修订解决的是方案表述和实施设计；性能目标须由后续试点验证。

| 原意见 | 修订内容 |
| --- | --- |
| F1 门禁与写入未互斥 | 调度表明确暂停全部参与指纹的写入，包括未跟踪 evidence 和已跟踪 ignored 文件 |
| F2 混淆并行门禁与 wave 合并 | 分开定义 worker 输入同步、真实身份、receipt 验证与译文合并边界 |
| F3 准备耗时归因和优先级不足 | 将 262 秒标为近似间隔，先测历史重放占比，再选择维护；增批与增加路数分别比较 |
| F4 吞吐基线未定义 | 规定准备至提交的墙钟、去重完成口径、基线补录方法和变量控制 |

此外，三个 reviewer 子进程改为保守的调度预算；批量准备明确只在单次调用内复用封存历史、更新本轮 obligations 并执行最终全量重放。

原审阅材料保持冻结。便于随仓库保存的 [Opus 原始意见](../evidence/plan-review/parallel-efficiency-revision-20261016/OPUS-REVIEW.txt) 与 [逐项处理记录](../evidence/plan-review/parallel-efficiency-revision-20261016/REVIEW-RESOLUTION.json) 一并保留；本修订不把原来的 `CHANGES_REQUIRED` 改报为 `PASS`。
