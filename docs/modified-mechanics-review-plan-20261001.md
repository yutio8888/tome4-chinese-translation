# 已修改机制译文快速复核执行方案

日期：2026-10-01。状态：执行方案，尚未开始译文复核。

本方案检查最近校对后仍有净变化的译文，优先发现技能、状态、装备效果等文本中会误导玩家的机制错误。采用“入选条目全量语义快筛、高风险逐条源码核验、低风险分层抽查”，排除纯叙事长篇 lore。交付覆盖清单与问题报告；本次编制文档不启动审核、不修复译文，也不启动生产队列或外部发布。

本方案是一次专项任务的安排，不修改角色、契约或生产完成条件。授权与不变量遵循 [AGENTS.md](../AGENTS.md)，操作与验收遵循 [工作流](agent-workflow.md)。

这里的“最近”具体指上述 BASE 至 TARGET，不包含 BASE 以前的全部校对。执行前将这两个完整提交号写入工作集；若当前任务明确要求其他起点，先重建选集。不得改用随 push 移动的 `origin/master`，也不因文档提交而自动扩大 TARGET。

以 BASE 与 TARGET 的净差异为主体：同一条多次修订只检查最终版本；中间修改后完全恢复的条目不重复检查。新增、删除、改键、参数重排也须登记，不能只统计中文 target 的变化。未改条目仅作为相关源码、完整句段或同一运行键的上下文引用，不自动扩展成全库审核。

本体、引擎及官方 DLC 中符合内容条件的改动均可入选。其他组件出现改动时也保留在分类账，明确其来源可用性；无法核验的机制记录为 pending，不静默排除。既有文档、未跟踪 evidence 及其他用户文件不并入本任务。

## 二 选集与分类

先以组件、section、source_tag 和英文 source 关联条目，再使用工具提供的 unit/revision 身份保存当前版本。裸行号只辅助定位；重复 occurrence 保留映射，不能只按英文去重。

每个候选记录两条独立分类轴：

| 分类轴 | 取值 | 判定规则 |
| --- | --- | --- |
| 内容范围 | mechanics | 技能、状态、装备属性与效果、资源、战斗规则、机制提示及相关名称 |
| 内容范围 | mixed | 对话或叙事夹带奖励、条件、数值效果；纳入机制句和理解它所需的完整上下文 |
| 内容范围 | excluded | 纯剧情、书信、背景、死亡修辞等；保存具体排除理由 |
| 内容范围 | unresolved | 无法可靠分类；在选集冻结前人工判定，不默认排除 |
| 改动类型 | semantic | 自然语言含义、名称或机制关系有变化 |
| 改动类型 | format_only | 仅允许的空格／排版变化，且其他字段与结构保持不变 |
| 改动类型 | structural | 新增、删除、source/source_tag 改变、args_order/special 变化或运行键变化 |

文件路径和关键词只用于生成分类候选。不得用字数阈值排除文本；长技能说明仍完整入选。名称只有在涉及技能、状态、装备类别或机制交叉引用时纳入，不顺带重新裁定剧情专名。

`format_only` 必须逐条证明：差异仅属于已列出的空格规则，placeholder、标记、换行及语义字段未变；不采用删除全部空白后的相等判定。无法证明就归入 semantic 或 structural。空格改动仍需检查技能升级预览的分词边界。

## 三 准备与导出步骤

1. 记录工作树、HEAD、BASE、TARGET、manifest 和规范译文文件哈希，检查是否存在活动生产 checkpoint。存在活动任务时先核对其恢复要求，不建立竞争写入者或删除 checkpoint。
2. 核对目标译文文件与 TARGET blob 一致。当前工具读取磁盘文件；HEAD 相同不能证明未提交译文没有混入。若不一致，使用保持工具依赖配置的隔离 checkout 或另建明确绑定快照的选集，不覆盖用户工作树。
3. 首次使用汉化工具环境时运行 doctor，再导出条目差异。以下为已核实的入口；此处命令只供正式执行时使用：

   ```bash
   git status --short
   git diff --stat
   git rev-parse HEAD
   git merge-base --is-ancestor 7c38a53b88a1c80d7d9b209f84c518ae9f6eac00 bfde8c53d50b065837ff34dc08639f7dbc5816f5
   python3 -B tools/i18n doctor
   python3 -B tools/review_diff.py --baseline 7c38a53b88a1c80d7d9b209f84c518ae9f6eac00 --batch-size 10 --character-budget 24000
   python3 -B tools/i18n lint --strict
   ```

4. 使用导出命令报告的实际目录，不猜测时间戳。保存 index、文件哈希及运行日志；同一输入不重复导出。
5. 补齐导出器没有提供的“修改前中文”和删除项。用现有 LuaJIT loader 按 BASE/TARGET 加载完整条目并比对多重集合；结合 `git diff BASE TARGET -- <相关规范译文文件>` 查改键、删除和非 t() 改动。没有唯一匹配的改键单独待判，不以相似英文自动合并。
6. 完成内容分类、改动分类、重复 occurrence 映射、排除理由和高风险标记，生成冻结工作集及其 SHA-256。记录导出数量与补充数量的对账关系。

工具边界：[`review_diff.py`](../tools/review_diff.py) 比较基线与当前文件，没有 `--target` 参数；主要导出当前侧新增／变化条目，不提供完整删除清单。它产生离线候选，不产生审核结论，也不直接生成可派发的 contextual v2 envelope。前后文补充、分类账和删除对账是宿主准备工作，不能声称已有一个命令自动完成全部步骤。

工具统一遵循 [i18n 使用说明](../i18n/README.md) 的 Lua 5.1/LuaJIT、LPeg 和环境约束。结构检查的失败按与本次改动的关联分类；基线问题单列，不能静默忽略或顺带修复。一次有界诊断仍不能归因的阻断项交回用户。

## 四 风险分层与检查清单

### 高风险项必须逐条查源码

以下任一条件成立即标高风险，不依赖快筛是否报告 ISSUE：

- 实质改变数值、单位、持续时间、频率、叠加层数、触发条件、目标、范围、先后顺序或例外。
- 伤害、治疗、护盾等复合描述发生语义变化；同句数值与持续时间的关系可能改变。
- 中文新增英文没有的范围、时序、因果或触发限定。
- args_order/special、占位符对应、动态拼接、运行键或 source_tag 有变化。
- 机制名称或装备类别变化可能改变玩家对适用对象的理解。
- 英中含义、术语、审核观察或源码之间存在实质冲突。

其余 semantic 条目为普通风险，仍逐条进行英文与当前中文对照。已证明的 format_only 条目全量做结构检查，并抽查实际展示。删除和改键必须核实调用与运行键是否仍有效。

### 每条语义复核都检查

| 维度 | 核对问题 |
| --- | --- |
| 主体与对象 | 谁发动、谁承受、谁恢复；敌我、自身、召唤物、所有目标还是首个目标 |
| 条件与概率 | 何时触发、何种攻击／装备生效、概率还是必然、条件是否覆盖整句 |
| 数量与时间 | 固定值还是百分比；每次／每回合／总量；持续时间、冷却、频率与上限 |
| 效果关系 | 增加／降低、施加／移除、叠加／替换、免疫／抗性／减伤、吸收／转移 |
| 限定与完整性 | 是否漏掉例外、否定、范围、结算先后；是否添加源码没有的限制 |
| 术语与引用 | 伤害、状态、资源、属性、武器类别是否适用于当前 scope/source_tag；关联名称是否对应 |
| 运行结构 | 参数类型与顺序、颜色与控制标记、换行、拼接宿主和重复运行键 |

宿主比较英文、旧译和新译，先记录“实际改变了什么”，再判断新译是否正确。独立 reviewer 读取冻结英文与当前译文及中性语境，不注入旧 finding、宿主判断或建议译法来诱导结果。

### 源码核验的最小记录

每项记录组件、公开源码路径、固定 commit 或文件快照哈希、关键定义／调用、证据摘录和结论。数值按“计算函数 → 传入参数 → projector/DamageType/timed effect 等消费者 → 显示句”追踪，明确 quantity kind 和单次／每回合／总量。

触发 [机制 claim 与运行时组合规则](agent-workflow.md#机制-claim-与运行时组合) 时，为相关 placeholder 保存 directional value-flow，至少包含 index、quantity kind、计算和消费锚点；不确定的类型写 unknown。若新增受跟踪 claim/fixture，再运行该规则指定的 claims check；不为本次只读报告随意改写共享 registry。

本体默认使用 manifest 固定 commit，不能用另一版本当前 checkout 的行为替代。DLC 文件哈希只绑定本次证据，不证明发行版本或源码仓库已固定；证据不足保留 pending。动态组合用代表性参数重渲染完整句，必要时记录最小游戏内验证步骤；未实际运行游戏就不标记“游戏内验证通过”。

## 五 批次与抽查安排

先取最多 10 条做试跑，覆盖技能、状态、装备、至少一种动态／数值组合，以及存在时的 DLC 和排版条目。试跑条目计入正式覆盖，不因试跑结束重审一遍。检查分类是否可靠、源码锚点是否足够、报告能否定位，再按相同规则完成余下工作集。

默认每个语义检查包不超过 10 条，并按导出器的 24000 canonical JSON 字符预算分包。分组先按组件和机制上下文聚合，再按稳定身份排序；资料过长时继续缩小。该预算只约束译文 item，源码与语境另行有界引用，不整文件堆入模型输入。

普通风险未报错项按“组件 × 技能／状态／装备／其他机制”分层，每层抽取 `min(n, max(3, ceil(n × 10%)))` 条查源码。排版项另按组件抽同样比例，优先验证技能升级预览及标记附近空格。使用 `SHA256(工作集哈希 + 条目稳定身份)` 排序取前 k 条，保存算法与实际名单，保证可重算。明显风险不得用抽样替代全查。

抽样发现一个 confirmed 机制问题，即将同层、同类改动模式的剩余条目全部升级源码核验；无法可靠缩小模式时升级整个层。每次扩查记录触发 finding、增加数量和完成情况。抽查比例是工作量安排，不是统计准确率承诺。

运行中记录导出、分类、语义核对、源码核验、裁决的实际耗时。首包完成后按剩余普通项、高风险项和抽查项分别估算工作量，不在条目数未知时承诺总时长。完成一个有界包即更新覆盖账和简报；不因批次切换重跑未变化输入的检查。

## 六 执行角色与契约选择

默认先由主代理完成选集和只读检查；小型有界工作集可直接交付。需要多批独立复审的大型工作集采用 Paseo，由 ORCHESTRATOR 冻结范围、核验和裁决；REVIEWER 只读。源码侦察如需委托只使用 SCOUT。本专项没有译文写入阶段，不创建修复 EXECUTOR。

采用 Paseo 前读取当时适用的 skill、角色和契约，建立 task ID、SPEC/PLAN/SCOPE/STATE，记录 cli 或 mcp 传输。运行配置按实时 profiles 与当前授权选择，不把旧交接中的模型或 push 授权自动继承到本任务。

独立机制复核使用 [contextual v2](paseo-translation-context-review-v2-contract.md) 的 `review_only`：每个有界 task 为单一 full，不把 implement 的四 lane 或 FINAL_REVIEW 收敛流程套过来。必要时分成多个独立 task，逐个闭合。冻结源码、相关术语正文和中性上下文，完成 preflight；reviewer 不读取旧裁决或当前可变译文。输出保持契约的 OK/ISSUE schema，宿主另记证据与影响，不要求 reviewer 增加 severity、建议修复等字段。

本专项不以 surface OK 决定高风险项是否查源码。若另行使用 [surface v1](paseo-translation-surface-screen-v1-contract.md)，它只承担表层筛查，禁止要求该角色补查源码；其完整任务和证据要求仍然适用。

所有 child 按[编排契约](paseo-orchestration-v2-contract.md)核验身份、只读边界、原始结果和归档；失败按 fresh retry 处理。不能仅凭 status 陈旧判挂起。无法确认生命周期时按 AGENTS.md reconciliation 和停止规则处理，不切回主代理绕过未归档 child。

本专项报告不修改 WP2-Lite catalog/queue/ledger，也不把结论计作生产 done/deep_reviewed。若明确切入正式生产审核，必须完整执行该流程的门禁、构建、证据、DONE_VERIFIED、提交/finalize 和重放，不能凭本方案的“快速”名称豁免。

## 七 裁决与证据文件

可重生成的导出、lint 日志留在 `.artifacts/i18n/`。实际执行时建立 `evidence/quality/modified-mechanics-review-20261001/` 保存人工分类、冻结成员、源码核验锚点和裁决；如目录已存在，先核对输入身份后恢复或另建唯一目录，不覆盖旧记录。

| 建议文件 | 内容 |
| --- | --- |
| `SCOPE.md` | 授权、BASE/TARGET、游戏来源身份、环境、读写边界及覆盖口径 |
| `workset.json` | 当前身份、文件定位、旧新译文、分类理由、风险、occurrence 映射及文件哈希 |
| `coverage.jsonl` | 每条的语义检查、结构检查、源码核验、抽样／扩查和证据路径 |
| `source-checks.jsonl` | 定义／调用锚点、value-flow、完整语境与反证、DLC 来源限制 |
| `findings.jsonl` | 观察、宿主裁决、影响、问题归因及建议 |
| `REPORT.md` | 覆盖统计、优先问题、pending、限制和后续修复候选 |

这些是宿主报告文件的建议格式，不扩展已有 reviewer 或 ledger schema。正式编排的 raw、envelope 和 STATE 继续使用各自契约路径，不用上表替代。

每项 finding 至少包含：当前 revision、位置、英文与旧新译文、具体误解、完整语境、最强反证、源码证据、宿主裁决及理由。证据状态与玩家影响分别填写：

- `confirmed`：证据足以确认错误；依次优先处理会改变操作决策的机制错误、显示／格式故障及其他明确失义。
- `pending`：来源、调用链或语境不足，说明缺什么证据和最小后续动作。
- `advisory`：可以澄清，但不能证明机制失义；不推动润色循环。

撤销的 observation 保留“撤销理由”，不算有效 finding。问题归因区分本轮新引入、旧问题仍存在、英文与源码既有差异；后者不能自动算成译文新增错误。确认前先检查整句是否已表达被指遗漏的条件，避免孤立逐词判错。

旧证据只供宿主复用或裁决参考。只有当前译文版本、源码身份、语境和实际核验 claim 全部一致时才计作可复用源码核验，并记录映射；旧 surface OK 不能算源码覆盖。既有术语与用户裁决按适用范围核对，不因个人语感重新开启专名统一。

## 八 验收与停止条件

普通只读专项完成须满足：

1. BASE/TARGET、输入文件哈希和实际读取版本一致；全部导出项、补充结构项和排除项对账，无未分类候选。
2. 所有入选 semantic/structural 条目完成整句语义核对；format_only 条目完成全量结构检查。
3. 所有高风险项及抽查扩查项均有源码结论，或有明确证据缺口的 pending；pending 不计“机制核验通过”。
4. 删除、改键、动态拼接、placeholder/markup/newline 等检查有记录；lint 失败有明确归因，不能把未解决的运行风险写成正常。
5. findings 有证据、反证和宿主裁决；报告分别给出快筛覆盖、源码核验覆盖、排版检查、排除、confirmed/pending/advisory 数量，并区分条目数与 claim 数。
6. 若采用 Paseo，各任务满足适用契约的结果、状态与生命周期完成要求；不得留未确认归档 child。

完成报告可带 pending，不要求问题清零。存在高影响 pending 时应写“只读检查完成，相关机制仍待确认”，不能宣称译文全部正常。只读验证按[验证矩阵](agent-workflow.md#验证矩阵)选择；本方案额外安排严格 lint 作为结构筛查，不因此启动完整生产构建。

边界存在实质歧义、出现重复实质分歧、需新术语或跨批次策略、门禁一次诊断仍无法归因、生命周期无法闭合时，执行 AGENTS.md 的停止与交回规则。完成不依赖决定的检查，提供具体证据和选项。译文修复、术语改动、提交推送及发布均按当前会话实际授权另行处理；本方案不推导这些授权。

最终交付为 REPORT 与可追溯清单。建议优先级供后续集中修复使用，不在审核期间边查边改，也不自动开启下一轮全库校对。
