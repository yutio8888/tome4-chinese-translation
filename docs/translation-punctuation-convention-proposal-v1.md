# 中文标点判据提案 v1（待批准草案）

**状态：待维护者批准。** 本文只提出规则与代价估算，不修改任何译文、术语库、lint 规则或
审核结论。批准前，`tools/i18nlib/lint.py` 与既有审核判据保持原状。

**背景：** [吞吐分析](review-throughput-analysis-20260905.md) §9 发现同一标点模式在不同批次
得到相反判定——早期批次将"中文句末使用半角感叹号"判为 confirmed 缺陷并修复，恢复后 20 批
对同型模式判 OK。AGENTS.md 将"确立跨批次统一策略"列为必须交回维护者的决定，本文即为该决定
准备依据。

**这份提案要解决的问题不是"哪种标点更好看"，而是"缺少成文判据导致同一模式在不同批次得到
不同结论"。** 无论批准哪一种取值，只要写成规则，一致性问题即解除。

## 1. 语料实测的既有惯例

对全量 29,828 条 catalog 条目统计（脚本见 §7）。

**句末标点映射**（仅统计含中文的译文）：

| 原文句末 | 译文句末 | 条数 | 占该原文类型 |
| --- | --- | ---: | ---: |
| `!` | `！` | 1,587 | 73.5% |
| `!` | `!` | 430 | 19.9% |
| `!` | `。` | 99 | 4.6% |
| `?` | `？` | 364 | 95.0% |
| `?` | `?` | 10 | 2.6% |
| `?` | `。` | 4 | 1.0% |
| `.` | `。` | 7,891 | 91.5% |
| `.` | `…` | 202 | 2.3% |
| `.` | `.` | 152 | 1.8% |

**句中标点**：

| 标点 | 全角（中文相邻） | 半角（夹在中文之间） |
| --- | ---: | ---: |
| `，` / `,` | 6,468 | **23** |
| `；` / `;` | 381 | **1** |
| `：` / `:` | 1,706 | **6** |

**结论：** 语料存在唯一的既有惯例——**中文语境使用全角标点，并保留原文的语气类型**。
句中标点的一致性接近绝对（半角占 0.35%）；句末感叹号是唯一有实质分歧的位置（半角占
19.9%，430 条），且这 430 条分布在 6 个文件中（mod-tome 341、orcs 48、cults 31、engine 8、
ashes 4、boot 2），不是某一份文件或某一位译者的局部风格。

因此本提案不是在两种惯例之间选择，而是把已经占压倒多数的惯例写成规则，并决定少数派
如何处理。

## 2. 提议的规则

| ID | 规则 | 判据 | 建议级别 |
| --- | --- | --- | --- |
| P1 | 中文之间不使用半角 `,` `;` `:` | `[CJK][,;:][CJK]` | **error** |
| P2 | 原文句末 `!` / `?` 的语气必须保留 | 原文末为 `!?`、译文末为 `。` 或 `.` | **error** |
| P3 | 含中文的译文句末不使用半角 `!` `?` | 译文末为 `!` 或 `?` 且译文含中文 | **error** |
| P4 | 不引入原文没有的首尾空白 | 译文首/尾为空白而原文不是 | **error** |
| P5 | 中文后的半角标点接 ASCII 需人工确认 | `[CJK][,;:][ASCII]` | warning |
| P6 | 换行数与原文不一致需人工确认 | 实际换行计数不等 | warning |
| P7 | 中文之间的空格需人工确认 | `[CJK] [CJK]` | warning |

**为什么 P1–P4 设为 error。** 四条都可对固定源码与译文字节客观判定，不依赖语感，且与语料
惯例的偏离度极高（P1 为 0.35%、P2 为 4.6%、P4 无对应原文依据）。P2 尤其明确：它改变了
原文的语气类型，属于对原文表面含义的改动，早期批次已按 confirmed 处理。

**为什么 P5–P7 只设 warning。**

- P5（297 条）：`法力:50` 这类"中文 + 半角标点 + 数值"的排版在技术性字段中可能是刻意的，
  不能一律判错。
- P6（409 条）：转义换行 `\n` 的计数在全语料**零不匹配**，说明引擎转义层没有问题；409 条
  全部来自 Lua 多行字符串的实际换行，中文排版重新断行往往是合理的。译文更多 260 条、
  更少 149 条，两个方向都存在，不存在单一正确答案。
- P7（211 条）：`generic acid retribution` → `通用 酸性反击伤害` 这类分类标签中的空格看起来
  是刻意的词间分隔，不是排版噪音。

**警告级别的含义**：不阻断门禁、不自动进入修复，只作为表层筛查的输入提示和选片信号。

## 4. 两个必须一并决定的问题

### 4.1 缺陷分档

AGENTS.md 的[复审收敛下限](../AGENTS.md)把缺陷分为两档：一级（fidelity、completeness、
terminology、runtime，以及 placeholder／markup／newline 不变量）任何 cycle 均可 reopen；
二级（grammar、conspicuous translationese）只在 `cycle <= 2` 可 reopen。

标点格式不在任何一档的现有列举中。建议将 **P1–P4 归入一级**，理由是它们与 placeholder／
markup／newline 不变量同性质：可对固定源码字节客观判定、不依赖语感、不存在两种都成立的
读法。P5–P7 为 warning，不进入分档。

若维护者不同意归入一级，替代方案是新设"三级：格式不变量"，只允许在条目尚未被接受时判定，
已接受条目不 reopen——代价是 §3 中的 56 条已审条目保持现状，一致性只对未来批次成立。

### 4.2 修复与审核的先后顺序

修改 target 会改变 `entry_revision_identity`，使该条目的既有审核状态失效。因此顺序决定
总成本：

- **先修复、后审核**（建议）：对未审的约 894 条，在它们进入审核队列前完成修复，新 revision
  直接进入正常审核流程，**不产生额外审核量**。
- **先审核、后修复**：这些条目会先被审一遍判 OK，修复后再作为新 revision 审第二遍，
  额外增加约 894 条的审核量——按当前 122 条/小时约合 7.3 小时。

已审的 56 条无论如何都需要 reopen 并重审，这部分成本不可避免。

**因此本提案的价值随时间衰减**：审核每推进一批，就有一部分待修条目被"先审后修"，成本翻倍。
按当前速率，每天约有 5.5% × 日审量的条目落入这一情形。

## 5. 落地步骤（批准后）

1. **误报标定。** 对 P1–P4 的全部命中做一次分层抽样人工核验（建议每规则 30 条），记录误报
   率。任一规则误报率超过约 5% 即降级为 warning 并重新设计判据，不带着已知误报进入 error。
2. **扩充 lint。** 在 `tools/i18nlib/lint.py` 新增对应 code（现有仅 `format-mismatch`、
   `format-shape-difference`）。error 级规则进入 `02-strict-lint` 门禁；该门禁当前耗时
   0.8 秒，新增规则的成本可忽略。
3. **一次性修复批次。** P1–P4 的修复在批次边界单独完成，不在活动 catalog 上改译文；
   走既有 EXECUTOR／独立复审／完整门禁／`DONE_VERIFIED` 流程。约 950 条按现行修复流程
   估计需要若干批，具体分批由执行时的实测决定。
4. **catalog 与队列重建。** 修复改变 target，需按标准流程重建队列；56 条已审条目按 §4.1 的
   决定 reopen。
5. **回归。** 修复后重跑 §7 脚本，确认 P1–P4 命中归零，并把 warning 级的三条纳入选片信号。

## 6. 风险与反对意见

- **误报率完全未标定。** §3 的数字是正则命中，不是缺陷。P1（30 条）和 P4（375 条）的判据
  最硬；P2、P3 存在少量合理例外（例如译文整体为英文专名、或原文感叹号本身是 ASCII 艺术
  的一部分），必须在 §5.1 标定后才能定级。
- **P3 影响 445 条，是最大的单项。** 若维护者认为句末半角感叹号可以接受，把 P3 降为
  warning 即可，规则集的其余部分不受影响——一致性目标仍然达成（因为规则写明了"可接受"）。
  本文推荐 error 的唯一理由是它与 P1、P2 共享同一惯例基础，例外会削弱规则的可解释性。
- **修复会改变已发布译文的观感。** 445 条句末标点从 `!` 变 `！` 是玩家可见的变化。这属于
  风格统一而非缺陷修复，若维护者对既有观感有偏好，应当在批准前说明。
- **本提案不涉及术语库。** 全部规则作用于标点与空白，不改变任何译名；不触发 AGENTS.md 的
  术语库停下条件。
- **P6 的 warning 可能长期无人处理。** 409 条换行差异若既不修也不判，会成为常驻噪音。
  可选做法是暂不引入 P6，等 P1–P4 落地后再评估。

## 7. 复现脚本

```python
import json, re, glob, collections
cat = [json.loads(l) for l in open('evidence/production-review-v2-lite/catalog/entries.jsonl')]
seen = set()
for d in glob.glob('evidence/production-review-v2-lite/batches/*'):
    for l in open(d + '/results.jsonl'):
        seen.add(json.loads(l)['entry_revision_identity'])
cjk = lambda s: bool(re.search(r'[一-鿿]', s))

RULES = {
    'P1': lambda o: bool(re.search(r'[一-鿿][,;:][一-鿿]', o['target'])),
    'P2': lambda o: o['source'].rstrip()[-1:] in '!?' and cjk(o['target'])
                    and o['target'].rstrip()[-1:] in '。.',
    'P3': lambda o: cjk(o['target']) and o['target'].rstrip()[-1:] in '!?',
    'P4a': lambda o: o['target'][:1].isspace() and not o['source'][:1].isspace(),
    'P4b': lambda o: o['target'][-1:].isspace() and not o['source'][-1:].isspace(),
    'P5': lambda o: bool(re.search(r'[一-鿿][,;:][ -~]', o['target'])),
    'P6': lambda o: o['source'].count('\n') != o['target'].count('\n'),
    'P7': lambda o: bool(re.search(r'[一-鿿] [一-鿿]', o['target'])),
}
for k, f in RULES.items():
    hit = [o for o in cat if f(o)]
    rev = sum(1 for o in hit if o['entry_revision_identity'] in seen)
    print(f'{k:4} 全语料 {len(hit):5d}  已审 {rev:4d}  未审 {len(hit)-rev:5d}')

# §1 的惯例统计
m = collections.Counter()
for o in cat:
    s, t = o['source'].rstrip(), o['target'].rstrip()
    if s and t and cjk(o['target']) and s[-1] in '!?.':
        m[(s[-1], t[-1] if not t[-1].isalnum() else 'ALNUM')] += 1
for k, v in sorted(m.items(), key=lambda x: -x[1])[:12]:
    print(k, v)
```
