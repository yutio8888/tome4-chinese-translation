# 投影重放优化方案：个人项目版

状态：修订方案，尚未实施，也尚未对本修订稿进行独立复审。

本稿结合 Opus 5.5 与 GPT-5.6-Sol（medium）对上一版方案的独立意见，以及主代理的源码核验。源码基准为 `dba3309b82255a9ec5501204e32d01d75ccaee3b`。本稿不修改现行门禁、恢复或发布契约；下文新增接口和缓存布局均为实施建议。

## 1. 目标与取舍

减少正常审核中反复验证相同历史证据的时间，保留从 Git 恢复审核进度的能力。按个人项目尺度，只建设实测能带来收益的部分。

决定如下：

- 不做 HMAC，不管理认证密钥。信任本机同一用户运行的程序，防范意外损坏、半写入、输入变化和实现升级造成的缓存过期。
- Git 中的已提交证据仍是长期依据。SQLite 保存运行队列，缓存只保存可删除的计算结果。
- 先计量并消除局部重复，再评估同一 commit 的跨进程投影缓存。跨 commit 内容缓存暂不实施。
- 保留独立无缓存重放、正式门禁和现有发布边界。缓存不替代模型审核、人工裁决、源码证据或门禁 receipt。
- 不增加常驻服务、第二个业务数据库、事件日志、密钥系统或通用依赖追踪框架。
- 每阶段结束后根据剩余瓶颈决定是否继续。达到可接受耗时即可结束优化，不以做完所有阶段为目标。

普通摘要不能抵御同时修改缓存载荷和摘要的程序；这是明确接受的边界。取消 HMAC 不放宽缓存输入完整性和失效要求，HMAC 本身也不能解决这些正确性问题。

## 3. 第一阶段：计量与局部去重

### 3.1 先记录真实调用

复用现有 [repair 计时包装](../tools/orchestration/run_repair_steps.py)和[单投影基准工具](../tools/orchestration/benchmark_projection.py)，增加最少的分段计时与计数，不先运行多轮完整性能实验。

记录一次有代表性的审核流程和必要的修复窗口：每条命令的实际参数、commit、工具墙钟、投影调用次数和耗时；投影内部记录 catalog 校验、migration 校验、publication 查询、batch 校验和汇总时间，以及 Git 子进程数量。分段口径必须不重叠，嵌套计时不能相加冒充总耗时。

同时核对实际调用是否使用了现有 [batch chain](../tools/orchestration/run_batch_steps.py) 和 repair chain。已串联的步骤不再计作潜在收益；阅读不可达代码不计作运行次数。

### 3.2 两项明确的局部改动

**复用当前 migration 边界的完整 reconciliation。** 首次验证 migration 时，仅为 `new_catalog_id` 对应当前 catalog 的唯一边界生成并保留 `_migration_rows(normalized)` 的完整有序 tuples。历史链传播继续使用紧凑映射。

当前紧凑映射以 old revision 为 key，保留四项 value，但没有 `reason` 和 `migration_id`，不能直接生成完整 SQL 行。不得猜测缺失字段，也不得为所有历史边保留完整行。无匹配边界返回空 reconciliation，多个匹配边界继续报错；直接调用原 reconciliation 函数时仍保留其独立验证能力。

**让进程内复用同时携带 projection 和 progress。** 当前 carry slot 只有五元组，不含 progress。需要复用报告的入口必须共享同次计算产生的两者；不能从最终 winners 猜算历史 progress，也不能为补 progress 再做一次完整重放。保持外部报告字段、排序和含义不变，调用者不得修改共享结果。

其他去重只对实际计数确认的有效路径进行。继续逐步检查 checkpoint、raw 文件、阶段状态、SQLite overlay 和锁；复用历史基线不等于复用活动状态检查。

### 3.3 第一阶段结束条件

比较同一输入下改动前后的投影结果、完整 progress、墙钟和峰值内存，再看真实命令序列的总耗时。

- 若正常审核等待已可接受，交付并结束，不建设磁盘缓存。
- 若剩余时间主要是不同进程重复计算同一 commit，进入第二阶段。
- 若剩余时间主要是必须独立执行的完整重放或门禁，磁盘缓存不是主要解法；针对最新 profile 做有界算法优化，不自动增加缓存层。

## 4. 第二阶段：只缓存同一 commit 的已提交投影

### 4.1 最小接口和入口边界

持久缓存只保存一次成功的独立完整重放得到的 projection、完整 progress，以及命中时必须复查的依赖对象清单。不从活动 SQLite 或 checkpoint 生成缓存，不保存未提交的 reservation 或审核结果。

原始无缓存算法作为参考路径保留。日常内部读取增加一个可显式关闭缓存的入口；保持已有命令默认语义，先通过显式开关试运行，验收后才为允许的内部路径开启默认缓存。

| 入口 | 第一版行为 |
| --- | --- |
| 普通 batch start、export/import、adjudicate、prepare 的历史基线读取 | 可命中同 commit 缓存；现有活动输入、锁、phase、SQLite 检查全部执行 |
| repair preflight 等普通历史基线读取 | 可命中同 commit 缓存，仍执行该命令自身检查 |
| `queue init/rebuild/check` | 保持独立完整重放，不读取持久缓存 |
| `finalize`、committed checkpoint 恢复及其他恢复/abandon 入口 | 第一版保持原有验证路径，不通过新磁盘缓存短路 |
| 普通 `queue status` | 先保留原有验证语义；不借性能改动悄悄降级 |
| 显式无缓存诊断/差分基准 | 禁止缓存读写，确保参考结果独立 |

生产边界的独立重放成功后可以写出缓存供后续普通命令使用，但必须在整次投影及动态依赖核验成功后发布。该副作用不属于显式禁止缓存读写的诊断模式。缓存写入失败只损失性能，不能使已经成功的业务操作被报告为失败。

入口允许表必须在实施中逐项核对调用链。正式门禁生成和 receipt 校验不在缓存范围内，不改变[工作流验证要求](agent-workflow.md#验证矩阵)。

### 4.2 输入身份和实现失效

缓存键至少包含：规范化仓库/工作树身份、解析后的精确 commit、缓存格式版本、验证器实现指纹和运行兼容信息。不能使用可移动的 `HEAD` 字符串、单个 revision ID 或数据库自报的 evidence head 作为完整键。

个人项目第一版采用保守的粗粒度实现指纹，避免维护精细依赖图：

- 对实际执行代码根下 `tools/` 的全部 Python 源文件，以规范相对路径和文件字节生成确定性摘要，覆盖 `i18nlib` 外的 contextual/surface consumer；新增、删除、未提交修改都必须反映在摘要里。
- 覆盖验证器实际读取的 schema、policy、容量注册表等非 Python 输入。默认保守覆盖 `i18n/quality/` 的普通文件，并在实施前核对是否存在目录外读取；发现遗漏先补入指纹或动态校验，不能默认缓存安全。
- 记录缓存 schema、Python 实现/版本、Git 版本及必要的运行环境边界。采用的解释器/依赖存在无法识别的非标准来源时关闭快路径。
- 指纹取实际执行文件，不仅取 Git HEAD 中的代码。长进程不支持运行中热更新验证器；检测代码/配置变化后拒绝缓存复用，重新启动命令。

该策略可能因不相关 Python 改动而失效，这是第一版接受的性能代价。不得只复用 benchmark 目前的三个实现文件摘要，也不以手动增加版本号代替实际输入指纹。

### 4.3 命中仍须检查的动态条件

同一个 commit 不足以证明本地环境未变化。命中时至少执行：

1. 重新解析目标提交，确认仓库、commit、实现指纹与运行边界匹配；writer 使用现有锁，写入前继续执行原有 HEAD/阶段一致性检查。
2. 检查 Git 环境适用性。第一版对 shallow、replace/graft、未核验的 Git 配置或环境覆盖回落原路径，不构建复杂环境兼容层。
3. 使用批量 Git 对象检查核对重放依赖对象的存在性和类型，尤其是 source evidence 引用的 commit/blob。依赖清单只能来自成功的完整重放，须覆盖所有会影响原验证成功与否的对象，而不只是当前 catalog。
4. 校验缓存格式、摘要、精确类型、行结构及身份绑定，再执行当前 checkpoint/SQLite 的独立核对。

当前 batch 校验还读取 evidence HEAD 树中 `tools/ci-gates.sh` 和测试文件的存在性。固定 commit 缓存将这一输入绑定在 commit 内；以后若做跨 commit 内容缓存，这些判断必须重新执行，不能按相同 batch 文件内容直接继承成功结论。

对象存在性检查依赖 Git 内容寻址的正常完整性保证，不每次对所有对象执行 fsck。缓存无法应对的存储故障仍通过独立无缓存校验及原 Git 错误暴露。依赖闭包或环境条件无法明确时，该入口不启用缓存。

### 4.4 保存、损坏和容量

建议独立目录为 `.artifacts/i18n/projection-cache-v1/`，与业务队列目录分开。使用严格 JSON 或等价非执行型格式，不用 pickle。载荷摘要解决意外损坏，不声明来源认证。

同目录临时文件加原子替换即可；不另建业务锁或事务日志。多进程同时计算同一键允许重复工作，最终只发布完整文件。缓存缺失、截断、错误类型、摘要不符、权限问题均视为 miss，返回原算法；原算法报错必须原样失败，不能返回旧结果或空状态。

第一版最多保留最近三个 commit 的缓存，设置总字节上限；上限在首个样本序列化体积测量后、实施验收前冻结。单项超过上限则不写缓存。淘汰只处理专用目录内符合命名规则的普通缓存文件，不追随 symlink，不触碰 evidence、queue 或 checkpoint。

实施时同步修改[正式方案 §2.2](translation-production-review-v2-lite-plan.md#22-唯一运行时数据)的运行时布局说明，并核对输出路径守卫、清理及恢复逻辑。缓存不是第二个队列或 coordinator checkpoint。此文提出布局，尚未修改该条款。

## 5. 暂缓的两项能力

### 跨 commit 内容缓存

不列入首轮实施范围。只有同 commit 缓存后，计量仍显示“允许使用缓存的新 HEAD 首算”占据显著耗时，才另行设计。

届时应先拆分纯内容验证和 HEAD/环境验证，分别证明依赖完整性。优先缓存独立、纯函数的 catalog/reconciliation 计算；批次验证涉及当前树、外部 consumer、规则注册表和 source evidence 对象条件，不能直接整体缓存。保留独立发布重放的成本要计入收益，不能把所有历史首算都算作可缓存部分。

### 快速进度查询

若查看进度本身仍造成明显等待，可单独增加显式快速模式。只报告本地队列/checkpoint 状态、对应 commit、是否同步和“未进行本次独立验证”。不得充当正式门禁、durable 证明或 writer 的历史基线。

第一版不改现有 `status` 的默认承诺；没有实际使用需求时不新增接口。

## 6. 验证与性能验收

### 正确性

每阶段以原无缓存算法为参考，比较完整 entries、overrides、reconciliation、progress、winner 顺序、失败类别及必要的恢复行为，不只比较数量。至少覆盖：

- 同一 commit 冷/暖命中、删除缓存后重算、缓存损坏和失败回算。
- validator/外部 consumer/规则注册表变化，即使 Git HEAD 不变也必须失效。
- HEAD 变化、只增删 gate/test 文件、证据撤销及 publication 歧义。
- source evidence 对象缺失、特殊 Git 环境回落、跨仓库缓存隔离。
- migration 无匹配/唯一匹配/重复匹配、完整行顺序、changed→reverted 不恢复旧覆盖。
- 活动 checkpoint 恢复、SQLite 非选中条目漂移、异常路径以及 progress 完整性。

现有有效测试直接复用；新增测试围绕失效、恢复和语义差分，不为缓存文件的每个字段写镜像测试。运行时实现涉及共享证据链，仍按工作流运行适用完整检查及独立复审，不因“性能优化”跳过。

### 测量口径

工具链总时间定义为一次审核流程中所有相关工具进程的墙钟总和，包含生产要求的门禁、finalize、rebuild 和恢复性验证；模型运行、人工裁决和空闲等待另列。修复窗口单独统计，不与审核批次混用。

固定一份输入及步骤序列，在隔离副本恢复相同初始状态后分别运行基线和候选。含发布步骤时还原相同提交/证据边界，不能声称整条有副作用流程始终处于同一 commit，也不能在生产工作树反复试跑。

采用三个串行样本的中位数作为主要比较值，同时报告范围和峰值内存；比较样本交替运行以降低机器负载变化的影响。冷缓存指应用派生缓存为空，不等于操作系统 page cache 为空；不清理全机 page cache，记录 OS 缓存未控制并保持两侧准备方式一致。暖缓存由同一份成功基线输入预热，预热成本单列，不藏进未报告阶段。

沿用现有基准工具已有输入/状态守卫，不改写旧性能任务冻结的验收阈值；本任务使用独立报告和阈值。

### 收益决策

令基线总时间为 `T = R + U`，其中 `R` 是允许优化的重复计算，`U` 是必须保留的门禁、独立重放及其他工作。仅缓存 `R` 的理论收益上限为 `R / T`；缓存命中成本另计。

先实测 `R`、`U`，再冻结当前阶段可达到的收益门槛。不再把“端到端下降 50%”作为未经测量的硬要求，也不以暖缓存单次下降代替完整流程提速。

硬性要求始终是语义一致、错误不被吞掉、删除缓存不丢成果。候选冷路径中位墙钟或峰值内存比同输入基线增加超过 10% 时先诊断，不默认接受。只有真实常用流程收益足以抵偿维护成本，才启用持久缓存；否则保留局部优化并停止。
